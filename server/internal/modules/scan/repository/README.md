# scan/repository

Repository conventions for the scan module:

- `scan.go` + `scan_query.go` + `scan_command.go`: three-way split for scan repository operations. The additive `CreateWithScanTasksAndPlans` transaction allocates scan/task identities, invokes Server `PlanTask`, and commits only when every executable task has one valid immutable plan while every planning-time skipped task has a reason and no plan.
- `scan_blacklist_snapshot.go`: Scan-owned immutable effective blacklist storage. `CreateWithScanTasksAndPlans` resolves the global-plus-Target-local union through its transaction context before inserting the Scan, then writes exactly one canonical snapshot in the same transaction as Scan, Tasks, and saved plans. The repository must not query current Policy while loading a snapshot, expose it through Scan/Task projections, or repair missing/corrupt data into an empty policy.
- `RefreshScanResultSummary` participates in result materialization's same-database transaction and must read transaction-local Snapshot rows after Snapshot and Asset writes; it is not an external side effect.
- `scan_mapper.go`: mapping between `persistence model <-> domain projection` (`domain.QueryScan/QueryTargetRef/QueryStatistics`) and create write models.
- `scan.trigger_type` is an immutable persisted provenance fact with the exact vocabulary `manual` / `scheduled` / `ai`. Create and read mapping must reject blank or unknown values; readers must not infer a fallback from mutable Schedule or occurrence state.
- `scan.input_source` is an immutable persisted execution-input policy with the exact vocabulary `scan_snapshot` / `target_inventory`. Create and read mapping must reject blank or unknown values; neither mapper nor lease read may infer a fallback. Saved-plan lease reads expose this trusted Scan-owned value together with the already validated canonical Target resource so the artifact resolver can select only the existing Scan- or Target-scoped cursors for `subdomains`, `hostPorts`, and `websiteURLs`.
- `scan_task.go`: executable task repository. Scan-level agent ownership is stored on `scan.agent_id`; terminal updates, cancellation, offline-agent recovery, and scan status counts read/write `scan_task` directly. A failed terminal row stores its stable kind, fixed message, and optional controlled `failure_detail`; all three are compared for exact replay before acknowledgement. Runtime task projections expose only whether immutable plan bytes exist; callers that need the plan must use the saved-plan lease boundary instead of loading the blob through ordinary task queries. `skipped` is counted separately as a terminal non-failure state and is never returned by pending-task claim.
- `engine_diagnostics` on `scan_task` is the one bounded Agent-owned terminal snapshot for an executable saved plan. Repository validation accepts only closed classifications and ordered per-result-type watermarks, persists it in the same fenced terminal write, and projects it directly to Scan detail. It must never reconstruct diagnostics from Agent workspaces, Engine logs, failure tails, or Server-side counter recalculation. The field has no separate store: hourly Scan history cleanup removes it with its owning task after the existing 30-day retention window; the Agent workspace 72-hour TTL is unrelated.
- `target_cleanup_cancellation.go`: the deleted-Target cleanup boundary locks Target, Scan, then Task, cancels exactly one active Scan transaction at a time, and returns only complete running-task assignment identities for post-commit best-effort Agent cancellation. It must not remove Scan, Task, progress, or Snapshot history.
- `persistence/scan_task.go`: persistence model for executable or intentionally skipped workflow step `scan_task` records; `skip_reason` stores non-failure applicability details and must not be mixed with failure fields. MVP does not create separate workflow/step execution tables.
- Planning-time skipped rows have terminal `status=skipped`, a stable `skip_reason` such as `user_disabled` or `target_not_applicable`, and no saved plan. Claim, assignment, retry, resource preparation, Agent session, and container paths must reject or ignore rows without a saved plan. Stage barriers remain application-level projections from child task states; this repository must not add a Stage status row.
- `saved_execution_plan.go`: read-only claim boundary for the plan bytes persisted at scan creation. It validates protobuf content and binds the plan's task/scan scope to the persisted row before returning it; it never recompiles package, workflow, config, Target, or resource facts.
- `saved_execution_plan_claim.go`: request-correlated container-execution claim transaction. It streams pending saved-plan rows, compares only `engine_api_major` with the authenticated fresh Agent snapshot, leaves incompatible rows pending, and CAS-binds the compatible task to Agent/process session/epoch/request ID. Replaying the same session request returns the exact persisted plan; no package/config/workflow reader is reachable from this path.
- `scan_domain_repository_adapter.go`: domain port adapter (`domain <-> repository`).
- `task_progress_log.go` + `task_progress_log_query.go` + `task_progress_log_command.go`: three-way split for task progress log repository operations. Every persisted progress event stores its required `scan_id` with its `scan_task` owner; `(scan_id, task_id)` is the database reference and `(scan_id, task_id, request_id, sequence)` is the replay key. This is required for aligned history partition routing and retention; scan-scoped reads use the persisted `scan_id` directly.

Constraints:

- Do not use `*_mutation.go` naming.
- Do not use generic filenames like `types.go`.
- `*_query.go` must not contain write methods; `*_command.go` must not contain query methods.
- Keep query/projection mapping in repository; wiring should only adapt interfaces, not move fields.
- `scan_task` is the persisted workflow step execution source. Do not introduce separate workflow execution tables, duplicate create-time queue projections, or alternate task-status sources without an explicit workflow execution model change.
- Scan history projects ordered, de-duplicated `plannedEngineIds` only from `scan_task.engine_id` rows with a non-empty saved execution plan. It must not use status, `started_at`, Agent events, `step_id`, or the current workflow to reconstruct historical execution.
- Scan detail joins the assigned Agent and its optional runtime row directly by `scan.agent_id`; it retains the canonical ID and `assignment_mode` when the Agent row is absent, projects the current display name/status without a snapshot, and derives deletion from row existence rather than an empty name.
- Scan result-summary cache refreshes belong in `scan_command.go` because they update the scan read model; result ingest may call them through a dedicated application port, not by making frontend/history callers recalculate counts.
- Fresh-install schema permits the temporary exact legacy claim shape (session epoch only), while any v2 claim marker requires the complete Agent/session/epoch/request tuple; a running task with saved plan bytes must carry that complete tuple.
- `scan_task` remains an unpartitioned execution table with single-column `id` primary key. Its extra `UNIQUE (scan_id, id)` exists only as the task-progress-log composite foreign-key target; history retention deletes it in bounded batches only after all aligned historical partitions are gone.
