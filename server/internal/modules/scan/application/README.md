# scan/application

通用规则请遵循：`server/docs/server-application-naming-template-v1.md`

scan 模块补充规则：

- **入口聚合**：facade 按用例维度拆分（`facade_scan.go`、`facade_scan_create.go`、`facade_scan_query.go`、`facade_scan_lifecycle.go`、`facade_task.go`、`facade_task_assignment.go`、`facade_task_status.go`）。
- **Facade 边界**：facade 只保留入口委派、少量返回模型转换和边界错误语义映射调用；重复的 scan/task 状态错误映射统一收口到 `scan_facade_helpers.go`。
- **服务编排**：`ScanFacade` 背后按 query/command/lifecycle/create 拆分 `scan_query_service.go`、`scan_command_service.go`、`scan_lifecycle_service.go`、`scan_create_service.go`；`ScanTaskFacade` 通过 `scan_task_bridge_service.go`、`scan_task_bridge_assignment.go`、`scan_task_bridge_result.go`、`scan_task_bridge_scan_status.go`、`scan_task_bridge_rejection.go` 共同承载 scan task execution 编排；`task_progress_log_service.go` 独立处理任务进度日志用例。
- **构造装配**：`bootstrap/wiring/scan` 是 scan application 对象图的 composition root；facade constructor 只接收已构造好的 service，不在 application 内部从 store/port 直接 `New*Service(...)`。
- **端口拆分**：端口按 scan/task/runtime-engine-selection 边界拆分（`scan_*_ports.go`、`task_*_ports.go`、`scan_task_*_ports.go`、`runtime_engine_selection_ports.go`、`scan_create_target_lookup_ports.go`）；scan create 的 workflow/engine catalog reader 端口及其投影视图集中在 `scan_create_catalog_ports.go`，不塞回 service 实现文件。
- **package catalog 依赖**：scan create 只通过 `ScanCreateWorkflowReader` / `ScanCreateEnginePackageReader` 读取 workflow definition 与精确 v2 package 视图；这些端口返回 scan application 自己的投影视图，不直接暴露 workflow manifest loader 类型。生产 reader 由 `bootstrap/wiring/scan` 适配；builtin engine definition root、`enginepackagecatalog.Load*` 和 repo root 推导不写入 application 编排逻辑，也不在 scan create 路径保留旧 package/runtime 兼容构造器。
- **scanWorkflow 资源名契约**：scan create API 接收的 `scanWorkflow` 必须使用 `contracts/resourcenames.ParseScanWorkflow` 作为唯一解析与校验事实源；application / handler / httpdto 不得手写 `scanWorkflows/{workflow}` 字符串拆分、typed ref 过滤或 ID 字符集规则，避免与 contracts-owned canonical parser 漂移。application 层可以包装错误语义，但不能复制格式判断。
- **动态配置结构解析**：`configuration.steps -> stepId -> {enabled, engineConfig?}` 的结构解析统一复用 `contracts/scanworkflow/configuration`；不得重新手写 top-level `steps`、未知 Step、entry shape 或 `engineConfig` 对象检查。`enabled: true` 必须提交完整配置，`enabled: false` 只能提交开关本身；Profile 输出显式的外层 Step 状态和完整 Engine 默认值，Scan create 要求请求为每个 Workflow Step 提交严格对象，不得补默认值或深层合并。已启用 Step 中，Engine Definition 声明 `requiredEnabled:true` 的单个 configSection 必须为 `enabled:true` 并带完整参数；校验失败必须在计划、资源绑定、Scan 或 Task 创建前返回，绝不能默认修复。前端禁用 Step 时可在当前会话保留只读草稿，但草稿不得进入请求或持久化；开发环境不兼容旧 shape。
- **创建期规划顺序**：Scan create 先解析全部 Step envelope 并检查至少一个用户启用 Step，再按冻结顺序分类。禁用 Step 只通过独立的 registration-exists reader 查询 Engine registration；不得读取 Definition、Package bytes、expanded cache、archive、资源或调用 `PlanTask`。只有启用 Step 才能进入 exact Package、完整 Engine config 校验、Target applicability 和 plan compilation；任一 Error 都必须原子终止创建。
- **scan workflow 模型**：普通 scan 绑定一条持久化 scan workflow；workflow 只含 stage / step 顺序和 `engineId`，不含 step-level `engineConfig`。创建普通 scan 时一次读取数据库 workflow、解析精确 Engine Package、校验完整配置，并在同一事务内物化 `scan_task` 与完整 saved plan。旧 `taskExecutionConfig` 字段只作为从 saved plan 导出的存储兼容投影；`skipped` 是 task-level terminal non-failure，不会被 Agent claim。MVP 只保留 `scan.status` 作为整体状态、`scan_task.status` 作为 step 执行状态；不创建独立 `workflow_execution` / `workflow_step_execution` 表。
- **Stage barrier 与 runtime 投影**：Stage 只由子 task 状态推导；`succeeded|skipped` 满足 barrier，`pending|blocked|running` 等待，`failed|cancelled` 保留阻断/传播语义，不新增 Stage 状态或 `stage.enabled`。planning-time skipped task 必须无 saved plan、不可 claim，runtime projection 使用可选稳定 `skipReason`；无 plan/session 的 skipped task 不进入资源、Agent、容器或运行日志请求边界。
- **冻结边界**：`scan.configuration`、Task 配置、精确 Package 和执行计划是同一创建事务的冻结结果，不是用户 partial intent。workflow 编辑、内置同步、Profile 变更和 Engine 升级只能影响后续 Scan；claim/retry 必须只读取持久化 saved plan。
- **PlanTask 边界**：scan-create 事务内为每个 workflow step 调用唯一 deep `PlanTask` compiler。compiler 只读取 canonical Target/workflow/config facts、精确 installed package、Server limits 和声明资源，返回互斥的 executable plan、planning-time skipped 或分类错误；只有 package 的 `supportedTargetTypes` 决定 applicability，`inputs[]` 不得被当作旧 profile 或 skip 条件。blocked task 也必须预存完整 plan。claim/retry 只能读取该不可变快照，不得重新解释 package、config、Target 或上游结果。
- **配置资源可用性**：Engine Definition 的非空 resource default 只是部署无关的 `fileName` preferred candidate，不证明部署资源存在，也不是可持久化的 `name`。scan application 拥有共享的 typed config-resource resolver 和 Workflow-level validator；普通 Scan 只为启用 Step 的启用 configSection 调用 resolver，并在 `CreateWithScanTasksAndPlans` 事务 finalizer 内验证 canonical `wordlists/{id}`、Catalog 行、常规可读文件及 size/line/SHA-256 后固定 descriptor，Scheduled Scan 保存期复用 Workflow-level validator 而不复制解析规则。确定不可用、校验依赖不可用和装配错误必须保持不同 typed cause，任何失败都不得提交 Scan、Task 或 plan。
- **Plan 后资源窗口**：saved plan 只固定 canonical `wordlists/{id}`、独立 plain `basename`、size、line count 和 digest，不保留字节。Agent 已验证的同 digest cache hit 可继续使用；cache miss 必须重新请求 Server 当前内容，Server 在 header 前预检 pinned descriptor，缺失或漂移返回 `DATA_LOSS`，Agent 不得启动容器或改用同名新内容、其他字典及 fallback。这里不新增 wordlist snapshot/retained-byte table、引用计数、保留租约、GC、schema migration 或 fallback source；Plan 提交到首次 materialization 之间仍存在字典删除/漂移失败窗口。
- **PlanTask limits policy**：`bootstrap/wiring/scan` 必须显式注入 Server-owned `PlanTaskLimitsProvider`；生产策略为每个新编译的 executable Engine plan 固定精确 14 天（1,209,600 秒），启用 v2 planning 时 application 立即校验四项 limit 均为正值并冻结一份 service 快照，scan-create 只把该快照复制进持久化 plan。请求/task config、环境变量、Agent 和 claim/retry 均不得覆盖或在持久化后重算，既有 saved plan 保持原值；testsupport 可用 `FixedPlanTaskLimitsProvider` 注入 2-5 秒预算。
- **Blacklist snapshot freeze**：每个 Scan 的创建事务先经 application 定义的窄 `EffectiveBlacklistPolicyResolver` 读取 global 与 Target-local Policy 的已锁定并集，并在 Scan/Task/saved-plan 提交前写入 Scan-owned `scan_blacklist_snapshot`。不得在事务外预读、在 batch 项间复用、在 Task/retry 时重读当前 Policy，或把 snapshot 暴露到 Scan/Task DTO、saved plan、Agent Context。
- **Execution input producer**：新 Engine Container 路径的 `subdomains`、`hostPorts`、`websiteURLs` 只由 Server 从已授权 Scan 持久化的 `InputSource` 选择读取边界并流式序列化：`scanSnapshot` 读取该 Scan 已最终化的 snapshot，`targetInventory` 在每次输入请求或重试时重新读取 canonical Target 的当前资产。来源只从 Scan/lease 读取，Agent 请求不得声明或覆盖它；canonical Target 只从已校验 saved plan 解析。两条分支都在 stream header 前加载并验证该 Scan 的 blacklist snapshot，只排除 matcher 命中的事实，不注入 Target baseline、不做业务规范化、不折叠或推断记录。Workflow 独占 Task 依赖的定义和判断；producer 与 artifact resolver 只为已经被 Workflow 调度并授权的 task 生成输入，不得查询、推断或重判前序 Task/Engine 状态。零记录是合法产品，Agent 仍原子发布零字节只读文件；查询、校验、黑名单、生产、传输或完整性失败必须在 Engine 启动前 fast-fail，绝不能发布部分输入、伪装为空输入或降级到另一来源。不得借此扩展 Endpoint 等输入角色。
- **失败分类与诊断**：`PlanTaskError.Kind` 直接使用稳定的 `server_package_load_failed` 或 `server_plan_compilation_*`；不得把 package load、plan compilation、planning-time skipped 混成同一结果。Agent terminal failure 持久化稳定 `failure.kind`、固定安全 message 和可选受控 `displayMessage`；后者必须是 Agent 的固定类别建议，Server 对其长度、空白、UTF-8 和控制字符 fast-fail 校验，并将其纳入终态重放一致性比较。scheduler rejection 可以把原始 error 返回当前调用栈，但不得把其文本写入 task/scan failure 或结构化日志。scan canonical failure 选择只认识 Engine Container taxonomy，不保留 `worker_start_failed`、`container_exit_failed` 或 Agent package resolve 别名。
- **状态命名**：状态更新方法必须带资源目标；更新 scan 用 `UpdateScanStatus`，更新可执行 scan task 用 `UpdateScanTaskStatus`（外部 task_id 传输名暂不扩散重命名，但语义指向 `scan_task.id`），避免在 task execution 编排中使用泛名 `UpdateStatus`。
- **模型命名**：输入输出模型按职责拆分（`scan_*_inputs.go`、`scan_query_outputs.go`、`scan_task_outputs.go`、`task_progress_log_inputs.go`）；domain alias 统一使用资源化 `*_aliases.go`（当前包括 `scan_create_aliases.go`、`scan_query_aliases.go`、`scan_task_aliases.go`、`task_progress_log_aliases.go`）；sentinel errors 按资源或用例放入 `scan_errors.go`、`scan_create_errors.go`、`scan_task_errors.go`，不新增泛名 `errors.go`。
- **对外边界**：scan task execution 能力继续通过 `ScanTaskFacade` 或 facade-backed boundary 对外收口，不直接暴露 `ScanTaskBridgeService`。
- **历史迁移**：历史聚合 alias 已拆分完成，后续新增继续保持资源化命名，不回退到泛名文件。
- **指定 Agent 绑定**：Scan create 可选接收 canonical `agent: agents/{id}`。创建时只校验 Agent 存在性；离线、健康和 Engine API 兼容性仍由 claim runtime 判定。省略时持久化 `assignment_mode=automatic`，指定时在 task 可领取前持久化 `agent_id` 与 `assignment_mode=pinned`。创建后的绑定不可变，不提供 Scan 重新分配操作。
- **创建来源**：每个内部 Scan create 输入都必须显式携带闭合的 `manual`、`scheduled` 或 `ai` 来源；不得默认化或从 Schedule/occurrence 反推。普通 Scan 不定义 quick/full 的 `scanMode`，也不得以 `creationMethod` 兼容别名恢复它；`scanWorkflow` 只描述执行编排。HTTP quick/batch 入口固定写入 `manual`，Scheduled Scan handoff 固定写入 `scheduled`，公共请求不得声明或覆盖该事实。
- **执行输入来源**：每个公共或内部 Scan create 输入还必须显式携带闭合 `InputSource`：`scanSnapshot` 或 `targetInventory`。该值独立于 `scanWorkflow`、Agent assignment、`triggerType` 与 Scheduled Scan `scanMode`，必须随 Scan 持久化；缺失、空值或未知值在边界 fast-fail，application 不得补默认。Quick create 传播其选择，Batch create 在请求级传播一个选择且不得把字段放入各 item，Scheduled Scan handoff 复制当时持久化的 Schedule 值。`targetInventory` 不是创建期快照，也不新增 Agent/Engine/protobuf 契约。
- **Scan detail Agent 投影**：详情直接返回 canonical Agent reference、`assignmentMode`、显式删除态，以及 Agent 存在时读时解析的当前名称、transport status 和可选 health state。不得保存分配时名称快照，也不得通过 Agent collection 补全或把页外资源判为删除。
- **严格领取与删除**：pinned Scan 的所有 executable task 只能由选定 Agent 领取；其他 Agent、离线或不兼容情况都必须保留 pending/blocked，不得回退或迁移。Agent 删除由 Scan-facing lifecycle port 与 claim 共用 Agent 行锁：未开始的 pinned task 以稳定 `agent_deleted` 失败并收敛 Scan；已运行 task 仍走既有 `agent_disconnected` session-fence 语义。

## Batch Stop Lifecycle

`POST /v1/scans:batchStop` is a synchronous, request-bound lifecycle command.
The handler accepts 1–100 unique canonical `scans/{id}` names and passes the
caller context through `ScanFacade` and `ScanLifecycleService` to one
Scan-before-Task transaction. Active (`pending`/`running`) Scans and their
active Tasks are cancelled with one stop timestamp; terminal Scans are left
unchanged and counted in `skippedCount`. A missing/deleted name or any write
failure rolls back the whole batch. After commit, eligible running-task Agent
notifications are best effort; delivery failures preserve committed state and
use the existing warning/counter path. The response contains explicit
`stoppedCount`, `skippedCount`, and `revokedTaskCount` fields and never
creates an Operation resource.
