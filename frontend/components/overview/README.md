# Overview Dashboard Rules

`frontend/components/overview` owns the local composition rules for the `/overview/` operational dashboard. This README is the near-code contract for information priority, section geometry, skeleton ownership, and loader handoff.

## Production Composition

- `app/overview/page.tsx` owns only the shared route shell and delegates the client-side header/section composition to `OverviewPageContent`. Because the overview command header has no description, the route shell keeps a `gap-4` (16px) rhythm on small screens. From `md` upward, `pt-5`, `gap-5`, and `pb-6` shift the command row 4px upward while preserving the content start, balancing the header's top and bottom visual whitespace without `PageHeader` margin overrides.
- `overview-lazy-sections.tsx` composes the dashboard in three rows: the runtime region first with `OverviewRiskSummary` followed by database and server-resource units, the operational row second with `AgentLocationMap` followed by `OverviewScanQueue`, and `OverviewAssetOverview` third.
- `OverviewPageContent` owns the manual page-refresh coordinator and passes only refresh state, completion time, and the command to `OverviewPageHeader`; sections retain ownership of their individual query rendering. The refresh timestamp starts at the first client mount and is replaced after a manual refresh concurrently re-fetches the eight first-screen query scopes, including the shared Agent cluster summary and complete location map, and waits for all of them to settle, so one failed source cannot block the others or leave the command busy. Existing source-specific polling intervals remain independent.
- `OverviewPageHeader` exposes the page refresh, add-target, and quick-scan commands. On wide screens it places the title/path at left, a node-management-style refresh control with the current page lifecycle or latest coordinated completion time at center, and the commands at right; all three columns share a bottom edge while the refresh control remains horizontally centered. During the server-to-client handoff the time may be temporarily unavailable, then the mounted page time is shown. On narrower screens the center control collapses into an accessible icon command in the action group rather than disappearing. Refresh feedback reuses the shared minimum-duration owner and must not reload the route, read a source timestamp as the page timestamp, reimplement drawer behavior, or add page-level error feedback that competes with section-owned states.
- `AgentLocationMap` owns the operational Agent surface. Its node counts, general execution capacity, cluster state, reason codes, and complete location coverage come from the shared authoritative `agentClusterSummaries/current` query; markers and connections come only from the non-paginated `agentLocationMaps/current` projection. It never traverses or aggregates the Agent collection and has no production coordinate fixture or default point. The surface intentionally has no separate panel title, header action, or bottom divider; node/capacity/coverage metrics stay in the header, while the health-status legend is a non-interactive bottom-right overlay inside the map content with no frame or fill. The legend contains only healthy, warning, and offline Agents; a positive `unknownCount` appears separately in the header as an unreported runtime state, so it cannot be confused with the Server's muted marker. The map fills the remaining height of the operational row on wide screens; narrow layouts retain the `248 / 100` fallback ratio. The dotted base, country paths, connection paths, and markers share one bounded `ZoomableGroup`, so wheel zoom and pointer/touch drag keep every layer aligned. Current and expired last-successful Agent locations remain visible, with freshness presented independently from transport/health; current locations have two low-opacity, offset expanding rings that do not require hover, while expired locations retain only their static dashed ring. The beacon is a bounded live-location visualization exception, respects `prefers-reduced-motion`, and does not imply task activity or network traffic. Agent labels describe geography as “基于公网出口 IP 推断” and use “观测出口 IP”, while the Server hover summary is the compact “位置未知（出口 IP：…）”. Neither prints coordinates or radius. An unknown Server location keeps an Agent-only map and removes all Server-origin lines; an offline positioned Agent keeps its marker but receives no line. Every eligible positioned Agent receives one visual scheduling-coverage line, and only `taskSlotsUsed > 0` adds a moving load segment. These lines are not topology, network paths, traffic routes, or actual task routing. Initial summary/map failures render section errors; refresh failures retain and visibly mark the exact last-successful snapshot until a later success replaces it. Server and its network paths use the shared `--muted-foreground` token so they remain secondary across light and dark themes.
- `OverviewRiskSummary` uses the existing global vulnerability-statistics query for reviewed and pending-review counts. Its `新增` value is source-owned by `changeVulns` but is intentionally non-negative: a net decrease is not newly discovered risk. It presents review counts whenever the query returns data without a cross-source synchronization message. If review statistics are unavailable, it renders an explicit unavailable status. If the primary asset-statistics source fails, the whole panel uses the shared section error state with retry instead of presenting the failure as an empty result.
- `OverviewRiskSummary` renders the severity distribution as a theme-aware Recharts donut with the total open-risk count in its center, keeps the five severity counts beside it, and uses the adjacent column for the seven-day open-risk trend, today's new count, and review metrics. Non-zero critical and high sectors are expanded by default; hovering another non-zero severity sector temporarily makes only that sector active, then pointer leave restores the default emphasis. The shared chart tooltip exposes the hovered severity, and the interaction is local to the visualization without altering source data. The vulnerability detail action sits in the panel header's top-right slot. The donut uses the existing severity color tokens and must remain data-driven; zero-count severities do not produce visible segments, and a zero-total dataset keeps the muted track visible. The trend reuses `useStatisticsHistory(7)` and shows an explicit unavailable state when history is empty or fails; it must not fabricate a production history series.
- On the first resolved render, the risk donut fades in once as one visual unit over `420ms`; it does not animate sector geometry, rotate, or replay during data polling. The reduced-motion rule renders it immediately.
- `OverviewAssetOverview` has no repeated card-level title: the asset and monitored-target metrics plus the adjacent seven-day trend establish the module context directly. Its skeleton must not invent a title or header action that the resolved card does not render. A primary asset-statistics failure uses the shared section error state with retry and must not be labeled as `暂无数据`.
- The asset metric pair keeps only its bottom divider and internal column divider; do not restore a top border now that the card-level title row is absent.
- `OverviewRuntimeDetails` is the first content surface after the command header; there is no separate summary readiness strip. It renders the risk summary as its leading slot, followed by database and server-resource units separated by dividers rather than visual card shells. `OverviewScanQueue` reuses the runtime scan cell in the operational row and names the panel `最近扫描`. It presents the full `running` / `pending` / `failed` / `cancelled` / `succeeded` taxonomy in one neutral five-column status band followed by a bounded source-owned recent-scan summary. It queries the same unfiltered first page and `createdAt desc` ordering as scan history, so it does not prioritize currently running work over newer terminal records. The recent-scan area labels target, status, and latest scan time once in a shared header attached directly to the status-band divider, with its own bottom rule; it does not repeat the panel title inside the list, and each row then shows those values plus a detail link. The list has a fixed six-row height and requests exactly six records; full scan history is available through the panel action rather than a scrollable overview list. Loading, unavailable, and successful-empty states remain explicit, and only the successful-empty state says `暂无扫描记录`. The history action remains the path for the full scan history beyond this compact surface. It intentionally does not render a redundant total-task footer. Database presents `状态` at left and its current value aligned to the lower right, then the established-connection ratio and established-connection count, the ratio meter, and finally task-backlog age plus probe latency; the connection metrics include both in-use and idle pool sessions. Resources uses a source-time header and three compact 18-segment rows, each with name/capacity then meter/percentage. The source units remain equal height, but their bodies must not share one generic distribution rule: scan and database use a shared `justify-between` body rhythm so their source groups have equal upper and lower separation; resource rows share the available height evenly. The two database diagnostics answer whether scans and scheduling are blocked or the database is becoming slow; lock waits, deadlocks, long transactions and optional performance signals remain in database-health detail. The neutral summary uses no status icons or status color; each recent-scan row reuses `ScanStatusBadge`'s `icon-only` variant, including scan history's canonical status glyph, color, and running-state rotation. The localized status remains the icon's accessible name and hover hint. The server-resource unit keeps labels, capacity detail, and percentage neutral; its meter is neutral below the overview-only 80% visual threshold and turns error-colored only at or above that limit. It reuses the same query hooks and renders an explicit unavailable state instead of treating a missing source as zero. Runtime-card prototypes and query-driven variant controls are not production UI.
- The `/overview/` composition is intentionally linear: the shared sections shell owns only the page-level top and bottom boundary plus horizontal/vertical dividers; individual section wrappers have no card background, border, radius, or shadow. The risk summary, asset distribution, and trend chart follow the same rule. The risk ring retains its circular center as visualization semantics; asset distribution uses the shared horizontal bar-chart foundation with direct quantity/percentage labels, while Agent highlights, scan source-owned status glyphs/values, and the server-resource shared segmented meter remain the bounded semantic-color exceptions.
- Existing legacy overview widgets are not part of the current `/overview/` composition unless this route explicitly mounts them again.

## Section Geometry

- `overview-section-layouts.tsx` is the single owner for overview page section grids and repeated internal geometry.
- The overview route inherits the protected shell's full-width workspace, while readable text, legends, semantic table columns, and compact metrics stay bounded by the existing panel grids and table min-widths. `OVERVIEW_AGENT_LOCATION_MAP_SURFACE_CLASS` and `OVERVIEW_ASSET_CHART_SHELL_CLASS` own the only overview-specific wide-container height growth (`@7xl/main:h-80`); the same constants must be used by resolved, loading, empty, error, and skeleton states.
- `OverviewOperationalGrid` owns the Agent-location-map and scan-queue relationship between the runtime-details and asset-overview rows. It is two equal-width columns only when there is enough width for both panels; narrower layouts stack the two panels.
- `OverviewSingleSection` owns the full-width runtime-detail and asset-overview rows. `OverviewRuntimeDetailsLayout` owns the unframed three-unit grid, while `OverviewRuntimeDetailsCard` is only the semantic source-unit wrapper and must not add a visual card shell. `overview-section-layouts.tsx` also owns the divider, scan-status, database-metric, and segmented resource-row constants so resolved and skeleton layouts stay aligned. Runtime units use a shared 24px section rhythm and 16px body-group rhythm. The three runtime headers share the same small direct-icon footprint and title baseline; the scan header uses a compact text link with a chevron matching the risk-summary action, while database keeps its compact arrow control with a Tooltip and accessible link to `/settings/database-health/`. The server-resource timestamp stays at the right of that same header row, and every unit anchors its details to the bottom baseline.
- Section panels use `OverviewSectionPanel`; do not wrap page sections in another card or recreate page-local panel shells.
- Responsive behavior must adapt content rather than hide it. On narrow widths, header labels may collapse to accessible icon commands, runtime cards reflow, and operational panels stack without clipping destinations or status text.
- The asset trend uses the shared short-date formatter for X-axis ticks so date labels remain readable after the asset section stacks on narrow viewports. Its area path is revealed once from left to right after the seven-day history first becomes ready, then stops so polling does not repeatedly attract attention; `prefers-reduced-motion` renders the settled chart immediately.

## Skeleton Ownership

- `overview-sections-skeleton.tsx` must reuse the same section wrappers and geometry constants as the resolved operational dashboard.
- The risk-detail and recent-scan-action skeletons use their resolved text-link line boxes rather than standard 32px button footprints. This prevents runtime and operational regions, and every lower overview section, from moving upward when data replaces the skeleton.
- The runtime, operational, and asset region wrappers carry the same named loading slots in the skeleton and resolved trees. Route geometry verification compares each region independently, so equal outer height cannot hide offsetting panel drift.
- The skeleton follows the same three-row order as resolved content: the risk summary first, then database status plus connection metrics, usage meter and two diagnostics, and segmented resource rows; then Agent-map and scan-queue rows; then asset metric blocks, distribution, and chart viewport. The skeleton uses the same direct-icon and divider geometry as the resolved view, so the handoff does not briefly recreate nested cards or filled action surfaces. Do not replace it with a generic `Card + Skeleton` loop after these sections have stable geometry.
- Map loading preserves the `248 / 100` world-map fallback ratio, total/capacity/coverage header geometry, and the bottom-right unframed status-legend overlay geometry without a bottom divider. On wide screens, resolved, loading, error, Agent-only, and unavailable states share the same fill-height geometry; the resolved map keeps the same region while the complete location-map query settles or contains no positioned locations.
- Text-bearing skeletons retain the corresponding production typography role's line box and replace only the visual glyph. Do not substitute fixed-height rectangles for content that controls a card or row's vertical rhythm.
- `OverviewSectionsLoader` remains the only visible first-screen loading owner. Do not add a second route-level skeleton from the shell or a child panel.

## Loader Handoff

- The dynamic import fallback stays `null`; `OverviewSectionsLoader` owns the first-screen readiness gate through `ContentHandoff`.
- `OverviewSectionsReadyProbe` returns `null`, preloads the lazy chunk, and unmounts after readiness so the lazy subtree owns live query observers.
- The required first-screen queries are asset statistics, seven-day asset history, global vulnerability review statistics, scan statistics, the Agent cluster summary, the complete Agent location map, database health, and runtime metrics.
- Readiness waits for every required query to settle. A rejected source must render its resolved unavailable state instead of leaving the whole dashboard skeleton permanently visible.
- The probe waits two animation frames before committing content. Do not mount the full lazy subtree hidden while loading or derive readiness from a callback that only runs after `ContentHandoff` renders its children.
